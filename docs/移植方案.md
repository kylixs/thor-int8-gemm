# Thor(sm_110) INT8 Triton fused-dequant GEMM 移植方案（2026-11-07）
> **EN summary**: Plan for porting the GB10 (sm_121) Triton fused-dequant INT8 GEMM to Jetson Thor (sm_110). Only `_C.cutlass_int8_dequant` is swapped (import-proxy, version-guarded, stock fallback). Stages P0–P5 with gates: P0 symbol/signature check ✅, P1 port (73.3 TOPS first try) ✅, P2 bit-exactness ✅, P3 local tile sweep (best 98.4, ×1.78) ✅, P4 engine A/B (superseded by cuBLASLt route), P5 upstream feedback (comfy-kitchen#312).


> 项目：把 [kanthai/gb10-comfyui-tuning](https://github.com/kanthai/gb10-comfyui-tuning)
> 的 `ck_int8_patch.py`（GB10/sm_121 验证过）移植到 Jetson Thor（sm_110）。
> 母问题：kitchen int8 在统一内存 Blackwell 上只有 ~50 TOPS（峰值 ~13%），
> 而 cuBLAS bf16 有 120 TFLOPS——见 gateway 仓 `docs/research/2026-11-07-gemm-optimization/`
> 与上游 issue [comfy-kitchen#312](https://github.com/Comfy-Org/comfy-kitchen/issues/312)、
> [#280](https://github.com/Comfy-Org/comfy-kitchen/issues/280)。

## 1. 上游方案要点（GB10 实测：72→170 TOPS，采样 −18%）

- 只替换 `_C.cutlass_int8_dequant` 一个符号：Triton GEMM（int8×int8→int32 累加）
  ＋ epilogue 融合反量化 `acc*xs*ws+bias`（fp32、与 cutlass 同序）；
- 部署＝`.pth` 导入钩子代理，版本守卫（0.2.37）＋Triton 失败回落 stock；
- 精确性：`torch.equal` 对 stock（两轮审计含 M>2³¹、K≤65536），整笔 H3 渲染
  latent/帧/音频一致；
- 非 contiguous 输入仍走 cutlass（我们的调用是 contiguous）。

## 2. 移植差异点（GB10 → Thor）

| 项 | GB10 | Thor | 动作 |
|---|---|---|---|
| arch | sm_121 | sm_110 | Triton 现编，无动作（验证 `triton.compile` 出 sm_110 cubin） |
| SM 数 | 48 | 96 | BLOCK/tile 参数可能非最优：首轮照搬，二轮扫 {64×128/128×128/64×256, num_warps/num_stages} |
| kitchen 版本守卫 | 0.2.37 | 0.2.40 | 放宽守卫到 0.2.40，**先核对签名** `_C.cutlass_int8_dequant` 是否同名同参 |
| kitchen 路径 | pip 安装 | `/home/nvidia/comfyui-libs`（宿主）＋容器 `/libs` | 代理按 sys.path 命中即可，无需改 |
| 调用入口 | cutlass_int8_dequant | 同（engine kernel `DefaultGemmWithVisitor` 即此路线） | bench 里 print 符号确认 |

## 3. 阶段与验收门

| 阶段 | 内容 | 门 |
|---|---|---|
| P0 环境与符号 | 主机2（空闲 GPU）bench 复用：`int8_linear` 9 形状基线 50 TOPS；确认 `_C.cutlass_int8_dequant` 被调用、签名一致 | 符号命中 |
| P1 移植适配 | 版本守卫/路径改 0.2.40＋Thor；`import` 后跑同 bench | **≥100 TOPS**（2×）才继续；失败查 Triton sm_110 编译 |
| P2 逐位校验 | 随机形状＋真实层形状 `torch.equal`（stock vs Triton） | 全等（GB10 已证可行） |
| P3 tile 扫描 | BLOCK/num_warps/stages 网格扫（主机2） | 取最优（目标 ≥150，对照 88% 峰值 ~340 的 GB10 比例） |
| P4 引擎 A/B | 主机1 空闲窗：`.pth` 代理挂进 comfyui-h3，同 seed 720p/5s 采样，打点 dit_step | 步时 −15% 以上＋质量门（稳定帧＋VLM＋人审） |
| P5 上游回馈 | 结果贴 #312/#280；若上游要 PR，把 tile 表做成 sm_110 条目 | — |

## 4. 风险

- 0.2.40 若改过 `cutlass_int8_dequant` 签名 → P0 就暴露，适配成本小；
- Triton 在 Thor 的 int8 dot 支持（`tl.dot(int8,int8,acc=int32)`）需实测；
- 统一内存下 L2 行为不同，GB10 最优 tile 未必 Thor 最优——P3 就是为此；
- 生产接入只走 `.pth` 代理（opt-in 文件存在才生效），**缺省零改动**。
